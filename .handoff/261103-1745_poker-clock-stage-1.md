# Poker clock: stage 1 implementation handoff

## Context and scope

Project: `/data/code/poker_clock`. The project directory was empty when planning began. The user wants a full-screen, self-hosted home-tournament poker clock, written in Go with Charm Bubble Tea. This is a planning handoff; no application code has been written. Do not start implementation without resolving the open decisions below where needed.

Build stage 1 as a single application binary. Target Linux, macOS and Windows. Use a pure-Go SQLite driver to simplify cross-compilation. There is no server requirement. An interactive terminal startup screen must work without CLI arguments. Provide optional Linux/macOS launchers that open a terminal from a GUI; the app itself remains one binary. Windows should be a console executable. GUI launchers should request a full-screen terminal where supported, falling back to at least 120 × 36 when possible. Terminal-launcher and sizing support depend on the desktop environment; document limitations. When launched in an already-open terminal, leave its window size and fullscreen state unchanged. Bubble Tea's alternate screen is not equivalent to an OS-level full-screen terminal.

Stage 2 has a separate handoff: `~/.agents/handoff/261103-1745_poker-clock-stage-2.md`.

## Tournament creation, persistence, and settings

- Startup offers **New** and **Load**, using an in-terminal file browser.
- New accepts an optional YAML template; if none is supplied, use an embedded default. Choose a destination for the new SQLite database. Load selects an existing tournament database. YAML durations use human-readable values such as `20m`, `10m`, and `90s` rather than integer minutes. YAML prices are euro amounts: `20`, `20.0`, and `20.00` all mean €20.00, not 20 cents or tenths. Parse the original decimal representation exactly, without binary floating-point conversion; still reject prices that are not multiples of €0.10.
- On creation, import the template into SQLite. SQLite is the source of truth for tournament configuration and state from then on; the YAML file is not required and must not be reread during play.
- Prevent two application instances from operating the same tournament database simultaneously and show a clear error. Preserve access for external read-only SQLite reports. The lock must recover safely after a crash and work on the supported operating systems.
- Each tournament has a required name, entered at creation, editable before play starts, and displayed on the main screen. Settings can edit the tournament configuration before play starts. Once play starts, the configuration stays locked, including after pauses and reopening an ended tournament. Settings can export the current tournament shape to reusable YAML, excluding the tournament name.
- Confirm destructive actions. Do not silently overwrite an existing database or template. Configuration editing, validation, exporting, and file errors need usable TUI feedback.
- Ended tournaments are read-only until explicitly reopened. Reopening requires an explanation that is nonempty after trimming and at most 200 characters; it is logged and restores the tournament paused, with configuration still locked. Previously finalized results remain part of history but are no longer final; recalculate on the next end and request tied-prize remainder choices again when needed.

## Default template

- Buy-in: €2, 1,000 chips. Rebuy: €2, 1,000 chips. Add-on: €2, 5,000 chips. The add-on's fivefold chip value is intentional.
- Every level lasts 20 minutes. No ante by default.
- Levels 1–3: 5/10, 10/20, 25/50. Then a 10-minute break.
- Levels 4–6: 50/100, 100/200, 250/500. Then a 10-minute break with a reminder to chip up the 5-value chip.
- Levels 7–9: 500/1,000, 1,000/2,000, 2,500/5,000. Then a 10-minute break with a reminder to chip up the 25-value chip.
- Levels 10–12: 5,000/10,000, 10,000/20,000, 25,000/50,000. The last playable level is held indefinitely rather than generating new blinds. The operator may add higher configured levels before play starts.
- Initial buy-ins and rebuys close at the **end** of the first break. One add-on per active player is available during that break. Use an explicit end-of-break deadline: when the following level is blocked, the break still ends and the deadline still closes.
- Payout percentages: 60%, 25%, 15%.
- Chip-ups are reminders only. Rounding chips remain on the table and are added to the first pot of the next level; do not adjust total chips in the app.

## Clock and blind progression

- Levels and breaks automatically advance when their timers expire. Start/pause uses Space. The first Space asks for confirmation that tournament settings will lock; later pause/resume presses are immediate. The first start requires at least two active players and an available opening blind level. Continuing requires at least two unique valid entrants, but may have only one active player after others bust. If corrections reduce valid entrants below two, pause and do not resume until there are at least two again. A clean app exit pauses and persists the timer. Checkpoint the running clock once per second. After a crash, reload paused at the last saved checkpoint; roughly one interval plus any write or scheduling delay may be lost. Time while the app is closed does not count as clock time.
- If the computer sleeps despite safeguards, pause and restore the last checkpoint on wake instead of counting sleep time or skipping levels; show the operator that the clock paused. Make a best-effort attempt to prevent both system sleep and display blanking on Linux, macOS, and Windows whenever a tournament is open, including while paused; release the inhibitions when it closes. Do not falsely promise support on all desktop environments. Notify the operator if inhibition or sleep detection is unavailable.
- A blind level is available only when total chips in play cover its small blind, big blind, and required antes. For a big-blind ante, add that ante once; for a per-player ante, multiply it by the number of active players, including sit-outs; with no ante, add zero. For example, 5,000/10,000 with a 10,000 big-blind ante requires 25,000 total chips. This total-stack test cannot prove individual players can cover their payments because individual stacks are not tracked. Normally `[L]` cannot select an unavailable level and must explain why. Recovery exception: when a correction leaves no level playable and registration is closed, `[L]` may select an unavailable earlier level to reopen registration; keep the clock paused and prohibit resuming until that level becomes available.
- When the next blind level is unavailable, hold the last playable blinds indefinitely. If it later becomes available, advance automatically; this can happen because chips are added or because a bust lowers the total per-player ante requirement. If the clock is paused when the level becomes available, wait until the operator resumes before advancing. The final configured level also holds indefinitely when it expires. During an indefinite hold, the large timer shows `HOLD` with the reason below.
- A break may finish even if its next level is unavailable. Mark the break finished, close its add-on window and any deadline at its end, and hold the previous playable blinds until the next level becomes available. Do not incorrectly treat this waiting state as a jump backward into a prior level or break.
- `[L]` can jump to a configured level or break and optionally set remaining time, without editing the locked structure. Applying the change preserves the clock's running or paused state. Rebuy and add-on eligibility follows the selected level/break, so a backward jump can reopen a window; the one-add-on-per-player limit still applies. Any such operator changes should be auditable.
- If a valid purchase or correction changes total chips or the active-player count so the current level becomes unavailable, accept the action, pause the clock, and require enough chips or a valid selected level before resuming. Examples: voiding a purchase reduces total chips; a new entry or a corrected bust increases the per-player ante requirement.
- Support no ante, per-player ante, and big-blind ante per level. Display the ante type and amount.

## Players, purchases, and busts

- `[P]` adds/removes players; no player-history view is required in stage 1. Names are unique within the tournament after trimming and case-insensitive comparison. Use stable internal IDs; a name change must preserve history.
- Registering a player and buying in are separate. A registered player becomes active on their first buy-in. At most one non-void initial buy-in per player. Later chip purchases are rebuys or add-ons; every purchase uses the configured price and chip amount, without per-purchase overrides. Before play starts, changing the configured price or chip amount for a purchase type is blocked until all non-void purchases of that type are voided; apply normal dependency and explanation rules. Store the actual transaction amounts in history.
- Until the rebuy deadline, both active and busted players can rebuy. A busted player's rebuy returns them to active status. Record every bust even if the player later rebuys. Initial buy-ins close at the same deadline.
- Templates can disable rebuys and add-ons independently; show disabled actions as unavailable. Initial buy-ins still use a configured registration deadline when rebuys are disabled. When rebuys are enabled, they share that deadline. Support a deadline at the start of a specified level or break, or at the end of a specified break; the last must remain distinct from starting the next level when that level is blocked. When enabled, allow at most one non-void add-on per active player, only during the designated break.
- `[O]` marks a player sitting out or returned. Record both events. A player who leaves remains active, counts toward player count and average stack, and can still finish in any position. Sitting-out players must pay applicable antes and blinds at the table. Blinds/chip deductions are managed at the table, not automatically by the app; the operator records a bust if their chips run out.
- A bust event supports multiple busters sharing the same winning hand and multiple bustees. Each bust requires at least one active buster who is not among the bustees. The operator orders bustees for finishing position and may mark ties. Track each player's final bust for provisional finishing places; a later rebuy reactivates the player and can change the provisional result. The operator can correct a single participant in a multi-player bust without voiding the whole event; retain the original, timestamp and explain the correction, and block it if it invalidates dependent later events.
- Removing a player is allowed only if no valid, non-void events depend on that player. Keep a removed player record/identity so voided history remains intact. The creation record itself must not make every removal impossible. If a removed player's name is added again, ask for confirmation and restore the original player record and preserved history instead of creating a second identity.

## Money, chips, prizes, and results

- Prices must be multiples of €0.10. Display all euro amounts with two decimal places. Use integer arithmetic, not floating point, for money and chip counts. The prize pool is the entire sum of non-void buy-ins, rebuys, and add-ons; no house fees or deductions.
- Total stack is total chips issued by non-void purchases. Busts do not remove chips. Average stack is total chips divided by active players, including sit-outs, displayed rounded to the nearest whole chip. Individual player stacks are not tracked. Handle zero active players without division by zero.
- Percentage tiers come from the template, are editable in settings only before play, and retain configured precision. Within each tier, percentages must be positive, non-increasing by place, and sum to exactly 100%; unpaid places are omitted. Reject invalid YAML and settings rather than silently normalizing them. Prize amounts are rounded to €0.10 but displayed with two decimal places, e.g. `€12.30`. Allocate €0.10 rounding remainders deterministically across prize places so payouts sum exactly to the pool; tied-player splits use the operator choice described below.
- Count entrants as unique players with a non-void initial buy-in; rebuys are not additional entrants. Support prize tiers keyed by inclusive minimum player count, using the highest threshold reached; require the first tier to begin at 2 entrants. Illustrative thresholds 2, 5, and 10 cover 2–4, 5–9, and 10 or more entrants respectively. Illustrative payouts are 2: 70/30, 5: 60/25/15, and 10: 40/30/20/10; these are examples, not the default. Preserve the previously agreed default of 60/25/15 as a tier beginning at 2. If corrections leave only one valid entrant, award that entrant 100% when the operator ends; the clock cannot continue with fewer than two entrants.
- If there are fewer entrants than configured payout places, renormalize the percentages of the available places proportionally. For example, 60/30/10 with two entrants becomes approximately 66.7%/33.3% before money rounding. Tied finishers split the combined prizes for their tied places; preserve the full pool when rounding. If a tied prize cannot be split evenly in €0.10 units, the operator chooses which tied player receives the extra €0.10 when the tournament ends. Before finalization, show that remainder as pending because the pot and places can change.
- Show provisional player finishing places and prizes from final bust order. The last active player is first. Results remain provisional until the tournament is ended; rebuys can change them.
- `[E]` is available only after play starts. It may end a tournament with multiple players still active; mark it incomplete and do not declare final standings. If all buy-ins were voided as mistakes and no active players remain, ending is also incomplete, with no winner. If corrections leave one valid entrant, the operator may end and award that entrant 100%. With one active player, the operator may finalize even while rebuys are open; explicitly warn that ending closes rebuys and finalizes the result. Confirm every ending. Incomplete endings also require an explanation that is nonempty after trimming and at most 200 characters; completed endings require confirmation only. Reopening is possible as described above. Before starting, the operator can exit without ending the tournament.

## Audit and timestamps

- Keep tournament state and its history in SQLite. Timestamp every stored item and change, including tournament/player creation and pre-start configuration changes, with a local wall timestamp with its UTC offset, elapsed tournament clock time excluding pauses, and elapsed real time since tournament start including pauses. Break time counts while its timer runs. Elapsed clock time measures actual running time and does not jump when `[L]` changes a level or remaining time. Items and events created before the tournament starts retain their wall timestamp and have null relative times.
- Purchases, busts with all busters/bustees and ordering/ties, sit-out/return, relevant clock/level changes, removal/cancellation, ending and reopening must be reconstructible for future reporting. Avoid silently rewriting history.
- Corrections void records rather than deleting them. Keep the original record and timestamped void; exclude voided records from current statistics. If voiding would invalidate dependent later events, block it and identify the records requiring correction first. Do not silently cascade voids.
- Every cancellation/void and player removal requires an explanation that is nonempty after trimming and at most 200 characters; Escape cancels the action. Preserve the explanation in the audit trail.
- Ensure SQLite transactions keep state, history, and derived statistics consistent, including crashes and failed writes. Persist a clock checkpoint atomically with each event that records elapsed clock time, so recovery cannot restore an elapsed time older than an already-committed event.

## TUI

- The entire app, including startup, file browser, dialogs, settings, and stage 2 features, must be fully operable by keyboard without a mouse.
- Full-screen, three-column layout, with 2:4:1 as a flexible target rather than a strict ratio. Minimum supported terminal: 120 × 36. Smaller terminals show a resize warning while the running clock continues. `[Space]` and `[Q]` must still work on that screen so the operator can pause or exit; retain the required confirmations. If a dialog was open when the terminal shrank, temporarily hide it and preserve its contents; the warning screen receives the shortcuts, and resizing restores the dialog.
- Left: buy-ins, add-ons, rebuys with number and sum in euros; total stack; average stack; prize pool; prizes for winners.
- Center: current small blind, big blind, ante/type at top; large level timer centered; current wall time, next level, next break, and next blinds/ante below. During a break, show `BREAK` in the current-blinds area and show upcoming blinds in the next-level area. Show the next break's label and tournament-clock countdown; if blocked levels make the countdown unknowable, show that rather than a misleading estimate.
- Right: button-like actions: buy-in `[B]`, add-on `[A]`, rebuy `[R]`, player `[P]`, level `[L]`, bust `[X]`, settings `[S]`, hand resolver `[H]`, Texas Hold'em rules `[?]`, start/pause `[Space]`, end `[E]`, and sit-out `[O]`. Add `[Q]` to exit without ending the tournament; it always asks for confirmation, even when paused or not started, and pauses/saves before exit. Use dialogs for applicable actions. The stage 2 hand resolver may be visibly unavailable in stage 1.
- `[?]` must display a full Texas Hold'em tournament rules reference stored in an editable repository Markdown file and embedded into the binary at build time. Editing it requires rebuilding. The user wants the implementing agent to write an original reference based on established rules; check authoritative sources, cite them as appropriate, and do not copy unlicensed material or imply unverified rules are authoritative.
- The clock keeps running while dialogs are open. Space enters a space in text-entry dialogs; the operator closes the dialog to pause with Space. Revalidate actions when submitted because deadlines, level availability, or player state may have changed while the dialog was open.
- Automatic level changes, break starts, and break ends show a visual notice and trigger sound. Sound is a global app preference, enabled by default and saved in the user's OS configuration directory; it can be changed during play and is not part of the locked tournament structure. Support a bundled sound and a user-provided WAV or MP3 sound, using the terminal bell as a fallback. Embed the bundled sound in the binary; handle unavailable/failed playback without blocking the clock and retain the visual notice. Terminal bells may be disabled.
- Distinguish keyboard shortcuts from typed input while a modal is active; handle resize, quit, errors, and terminal restoration safely.
